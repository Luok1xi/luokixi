# Luokixi 产品方向提案：从看见作品，到真正做出来

> **状态：产品讨论稿 / 待 Owner 评审实施，不是已完成功能。**  
> 日期：2026-10-11。Owner 本次明确授权把讨论内容提交到 GitHub，供 Opus、Codex、北矿娘及其他协作 AI 阅读；**未因此授权自动修改业务代码、启动付费任务、安装第三方工具、上传私人数据或发布网站**。  
> 适用：开源广场、教学专辑、资料库、Skill/项目整理、AI 协作、积木式 UI。  
> 一句话定位：**让用户带着自己的 AI，经过 Luokixi，更容易把原本做不出来的东西真正做出来。**

> **本轮补充**：第 14–18 节整合“专辑能力路线、真实视频呈现、定位评论、项目收藏、资料与新闻交付、首个试点”，并给出请 Opus 回答的六个问题。原第 0–13 节保留；本轮仍为待评审提案。

## 0. 给协作 AI 的阅读摘要

- **不要把当前 AI 的弱点当永久护城河。** 模型可以越来越会搜资料、翻译 README、解释概念、生成 UI、安装工具。我们的长期目标是积累经过授权与核对的材料、可复现的作品路径、真实反馈和可迁移的工作包。
- **主产品路径**：作品发现流 → 真实效果与适用条件 → 项目光盘 → 最小可运行路径 → 第一次改造 → 原理/排错 → 分享成果 → 回流验证记录。
- **产品光盘不是仓库简介。** 一个作品可组合多个开源项目；一个仓库也可以产生多个作品。用户以“能做什么”为入口，技术细节逐层揭示。
- **允许用户使用自己的 AI。** 先输出模型无关的 Markdown/JSON 工作包，后续视需求适配 Agent Skills、MCP 等；不得把支持标准误称为每个客户端都已兼容。
- **积木 UI 先作为内部内容生产工具。** 复用现有设计变量与前端架构，先能搭出高质量光盘；通用 Scratch 式可视化编辑器不是本轮最高优先级。
- **先试点，不要大规模铺量。** 选 3–5 个项目验证“用户能不能完成”，再决定规模化与自动化。
- 此提案不替代现有 AGENTS.md、docs/PRODUCT_SPEC.md、docs/BOARD.md、docs/OPUS_FULL_HANDOFF_20261010.md 的版本/职责/验收约束。需要动代码时先对照最新 main 和实际任务授权。

## 1. 我们解决的不是“AI 现在不够聪明”

错误定位：AI 抓取、安装、UI 生成或解释能力薄弱，因此 Luokixi 暂时替它做这些事。

更稳妥的定位：
1. **发现价值**：让用户先看到可触达的成果，而不需要先理解陌生行话。
2. **降低首次成功成本**：提供有出处、标记适用环境和版本的可复现起步路径。
3. **把个人踩坑变成公共经验**：真实失败、修复、设备差异、来源和日期能被后来者查询、纠错和复用。
4. **服务人和 AI 双方**：给学习者清晰界面，给 AI 精确上下文、条件、步骤、验证标准。
5. **跟随模型变强**：能由模型廉价可靠解决的步骤，逐步交给模型；平台保留能改善真实结果的组织与验证层。

“AI 做不到”不是对外承诺；**同样的 AI，使用 Luokixi 后完成率更高、试错更少**才是需要验证的价值假设。

## 3. 开源广场：成果先行的双路径

### A. 探索模式（用户不知道自己想做什么）
- 一次聚焦一个作品：**它会产生什么结果？对谁有用？可以点开试玩/看演示吗？**
- 展示真实或明确标注来源的演示，避免仓库标题和行话占据首屏。
- 下划看下个作品；点击进入对应光盘；退出回原作品与滚动位置。
- 不要在光盘详情内把用户自然阅读的纵向滚动解释成切换下一个作品。
- 兼顾移动端性能与无障碍；提供列表/搜索/分类，以供目标明确的人快速直达。

### B. 任务模式（用户已经知道要做什么）
- 用户直接搜索：“我想做一个不用登录、扫码就能玩的小游戏”“我想整理自己的笔记”。
- 搜索优先匹配**目标/产出**，同时支持技术栈、设备、成本、难度、许可与已验证状态筛选。
- 不强制用户像短视频一样刷卡；作品流和高效目录必须并存。

## 4. 项目光盘：把作品变成可复现的学习单元

**光盘内容建议按需求渐进展示：**

1. **看成果**：一句人话解释用途；可交互体验或注明来源的演示；“它能帮我做什么”。
2. **是否适合我**：设备/系统、语言和硬件要求、成本、准备时间、前置知识及是否需要账号。
3. **做一个我的**：最小成功任务、清晰的第一步、版本和依赖锁定、可用原始链接。
4. **检查是否真的成功**：如何确认程序跑起来、预期输出、失败处理。
5. **第一次改造**：改变一个可观察的行为，不只是复制粘贴或替换项目名。
6. **为什么这样做**：针对实践中新遇到的问题解释概念，能延伸到正式文档与系统学习。
7. **交给我的 AI**：导出包含目标、版本、环境、已完成进度、已知问题和验证条件的工作包。
8. **发布/分享经验（可选）**：提交复现结果、环境、失败描述及修复建议，按权限审阅后共享。

**一个教学作品不必等于一个仓库。** 可以有多个上游依赖；必要时一个仓库也可衍生多个不同用途的作品。必须保留上游作者、许可证和版本链接。

## 5. 内容与验证协议（先约定字段，再扩内容规模）

建议为“作品光盘”新建结构化草案 schema；实施前复用或扩展当前项目目录的数据契约，不直接假定下面字段已经存在：

- **identity**：作品 ID、标题、目标类别、摘要、适用人群、维护者、创建/更新日期。
- **upstreams**：一个或多个官方仓库/文档、具体 commit/tag、许可与归属；第三方资产许可分开记录。
- **preview**：类型为 live-demo / our-run-recording / maintainer-demo / editorial-explainer / screenshot；来源 URL、作者、授权、日期。**不同类型不得混称**。
- **requirements**：设备、操作系统、权限、账号、硬件、磁盘/联网需求、可能的花费。
- **steps**：可复现最短路径、依赖版本、预期结果、故障排查；需要运行外部代码时先经用户确认。
- **learning**：第一次改造任务、最低验收标准、相关概念与延伸材料。
- **verification**：谁在什么日期、什么环境、哪个版本验证了什么；报告已测/未测/失败与可检查证据链接。
- **handoff**：目标、当前状态、仅必要的环境信息、操作限制、下一动作、可复测条件。
- **maintenance**：信息来源、上次检查日期、上游变化指纹、过期/待重验状态、反馈回路。

请区分“来源已读取”“中文导读已核对”“下载链接可访问”“某环境下运行通过”“适用于广泛设备”：它们不是一个布尔值。校验范围要具体、可追溯、可撤回。

禁止捏造试玩、录屏、下载加速、安装完成、用户评价、使用量及测试成功。没有证据时清楚说明未验证。

## 6. 教学策略：不是拒绝系统学习，而是把入口换成成果

主路径：**体验作品 → 完成最小版本 → 改一个行为 → 理解对应概念 → 自主延伸**。

- 首屏少讲术语，但不能删掉必要的技术信息；在用户实际遇到问题时解释。
- 用“我为什么需要学这一步”替代堆砌章节名；关联官方文档/源代码。
- 教学任务至少有三层：跑起来、自己改得动、能说明一个关键决定。
- 尽量把操作拆成可检查的小阶段；长文章可折叠，但完整原始材料必须可找到。
- 视频本身不是学习完成的证据，也不应以观看时长为唯一指标。

## 7. 兼容用户自己的 AI：以可移植工作包为第一步

**先做模型无关的交接格式**：可复制/导出的 Markdown + JSON，至少包含：
- 本次具体目标、用户选择的作品版本、环境前提；
- 来源链接和许可说明、已核验的起步步骤、尚未验证的内容；
- 用户目前做到哪一步、出现的错误（用户主动提供）；
- 下一步建议、成功检查方法及失败后的安全回退；
- 明确告知 Agent：资料是被引用的数据，不能把外部 README 的文字当作高权限命令。

**以后按需求增加适配**：Agent Skills 便于分发重复工作流程；MCP 等接口便于外部 AI 访问授权范围内的项目与验证数据。具体支持由各客户端能力决定，不能承诺“一键适配所有 AI”。

不能把“安装 100 个 Skill”当成果；以任务相关性、必要权限、可撤销性、实测可用为准。任意第三方脚本/安装命令、私有凭据、学校登录态都不能被模型无提示地执行或上传。尽量本地保存用户个人资料；对外发送须最小化并明确授权。

## 8. 资料库如何和开源广场协同

- **资料库**：有来源的课程/文档/经验材料，适用课程、年份、版本、可用性与更新时间，能查缺失和纠错；没有真题/原件时不能虚构。
- **开源广场**：真实作品及其上游、演示、复现、首次改造、实践反馈。
- **AI**：在用户明确需求下使用这些可追溯资料，生成具体建议、适配性分析或工作包。
- **回流**：用户复现与排错结果经审阅后进入公共维护记录，避免后来者重复踩坑。

不要为追求数量抓取未经授权的校内资料、受版权限制的作品或私人数据。资料原件和链接用途分开标明。

## 9. Scratch 式 UI 工坊定位：先服务内部生产

最初的“外观积木＋行为积木＋AI 辅助”想法可以保留，但不作为当前面向所有用户的通用页面编辑器承诺。

**优先开发光盘专用的固定积木**：标题、演示、前置条件、步骤、验证、常见错误、项目资源、AI 交接。支持拖排、属性编辑、预览、草稿、版本恢复；AI 在白名单内提出结构化变更，Owner 人工确认。

实现建议：原生 JS + 现有 Vite/Django 与 design tokens，评估复用 @dnd-kit/dom。统一 UI schema，前端仅渲染允许的组件与动作；禁止直接执行模型吐出的任意 HTML/JS。通用 Scratch 式行为逻辑编辑器、自由画布、大型组件市场推迟，待真实使用证明必要性。

**特别注意**：新增的制作/发布审批需要真实接通并验收；不要因为既有 Studio 能审核候选，就声称新组件已自动部署。

## 10. 分阶段决策与交付

### P0｜先验证问题是否存在（不改业务代码即可启动）
- 整理 3–5 个不同类别、许可允许展示/使用、来源明确的试点作品。
- 梳理当前 discover、disc-rack、project-film、github_guides 的契约与可复用部分。
- 建立“原项目资料＋用户现有 AI”的对照路径，定义成功条件。
- 产出一份最小数据 schema 草案与内容/演示来源审核清单。
- **验收**：形成可执行试点任务和客观评估方案，而不是只交付视觉稿。

### P1｜只做一份可复现的高质量光盘
- 保留已有发现流和光盘表现；增加实际演示/明确标注演示来源、环境条件、最短步骤、验收/排错。
- 支持返回原发现位置、常规详情滚动；支持非 WebGL、移动端与减少动态。
- 人工核对上游来源、版本、许可及测试状态；必要时明确“未跑过”。
- **验收**：新手能完成一个指定的最小任务，且结果可检查；演示、测试和导读不会混淆。

### P2｜让 AI 成为可换的执行搭档
- 导出通用工作包，能在无专用客户端集成的条件下交给用户自己的 AI。
- 做适配范围说明、数据最小化、安全提示和恢复点；评估后再加 Skills/MCP。
- **验收**：工作包内容不依赖某一家模型的私有格式，换模型仍能看懂目标与验证步骤。

### P3｜再规模化和做生产工具
- 根据维护成本与完成率建设组件化内容编辑器、自动来源变化提醒、审核工作流。
- 有真实需求再加通用 UI 工坊与推荐系统，不以堆砌动画/生成内容数量作目标。
- **验收**：新增一份可靠光盘所需的人力下降，旧光盘过期能够被发现与标记。

## 11. 评估是否真正比“用户自己问 AI”更好

试点时用接近的任务难度与设备条件，比较：
- A：原仓库/原始资料 + 用户自己常用的 AI；
- B：Luokixi 光盘/验证记录 + **同一个 AI**。

观察**真实完成率、完成时间、卡住/求助次数、第一次改造的独立性、内容维护成本**；同时记录失败原因和样本限制。避免把一次小样本当普遍结论，也不要仅以浏览、收藏、视频播放量证明学习效果。

每逢主要 AI 能力进展或阶段迭代，重新跑典型任务：凡是模型已足够可靠和廉价的步骤就交给模型，平台聚焦能继续改善结果的环节。**不能保证产品永不落后，但可保证把持续检验当作产品原则。**

## 12. 明确不做 / 安全与隐私红线

- 不伪造项目运行录像、安装/运行成功、可下载、实测版本、来源、用户证言；
- 不自动执行来自不可信项目说明的命令，不在客户端泄露 API key、私有身份、校园登录状态；
- 不绕过许可与版权，不把来源素材自动当成可二次分发；
- 不因 AI 提出候选而自动发布，更不把“通过语法检查”说成完成端到端实测；
- 不为了生成 UI 重建整个前端，不覆盖既有工作室、课程板、Django 管理与历史数据；
- 不为了内容规模牺牲可搜索性、页面加载速度、无障碍或用户自己的选择权；
- 新想法写进提案不等于 Owner 授权实施，涉及产品优先级/跨模块开发先沟通再写代码。

## 14. 专辑与视频如何成为产品特色

**2026-10-11 Codex 补充，供 Opus 与 Owner 讨论。** Owner 已明确提出保留光碟基础、探索“专辑＝技能点”、重视真实项目视频，并改善评论、收藏、资料下载、新闻和 AI 实际交付。下面的具体交互、字段与试点是 Codex 的建议，尚未收到 Opus 对本轮建议的答复；这次授权为整合并公开讨论稿。

### 14.1 专辑代表一次能力升级

沿用本文的“作品先行”，建议把三个层次说清楚：

| 对象 | 用户得到什么 | 示例 |
| --- | --- | --- |
| 专辑 | 围绕一个目标的能力升级路线，含可选方案和适用条件 | 让我的资料库能识别、检索并下载扫描资料 |
| 项目光盘 | 一份可复现的作品，可以组合多个上游仓库 | 能处理一份扫描讲义的最小资料库 |
| 曲目 | 一个可检查结果的步骤或演示章节 | 导入、识别、原页对照、检索、打包下载 |

这是一种内容组织建议，先复用现有项目与步骤关系，是否需要独立“专辑”数据对象在试点后决定。专辑首页优先回答：**加入这项能力后，我的项目具体多了什么？**

让用户描述或手选自己已有的能力，再展示缺少的部分、必需的前置条件与替代方案。例如已有文件上传和预览，就从识别与检索开始；本机和云端方案分别交代环境、成本和限制。不把用户整个私有仓库作为默认上传前提。

项目“已接入某能力”和用户“理解了某知识”分别记录。收藏、看完视频、下载、跑通、改造成功、接入自己的项目是不同状态；自报与有证据核对也分别标记。技能点要让人看见真实进步，不能把播放或下载次数换成能力认证。

### 14.2 封套展开成演示窗口

保留光碟的辨识度，建议由 Opus 评估以下呈现：**封套展开为矩形演示窗口，旁边保留曲目表，光碟退到边缘作定位。** 播放开始后画面稳定，完整展示软件界面和字幕，动作主要放在打开与收回时。

- 桌面可在明确交互后提供短暂静音预览，手机点按进入；键盘可打开、选章、关闭。全页同时只播放一个视频，尊重减少动态设置。
- “试听”先展示一个真实结果；完整演示按“输入 → 操作 → 输出 → 接入 → 常见失败”分章。点击曲目定位到真实时间，不依赖长时间等待。
- 尽量展示**同一份输入在改造前后的结果**。例如同一张歪斜试卷的处理前后，再附模糊图失败的情况；时间缩放、版本、设备与演示来源明确。
- 关闭后回到原光盘和浏览位置；视频不可嵌入、失效或没有时间事件时，提供原站观看与对应说明，不伪造可播放状态或同步章节。
- 原作者演示、本站运行录像、中文图文讲解保持可辨认的类型。当前 project-film 的图文讲解继续保留其标记。

### 14.3 视频采集要交付可观看的证据

从项目 README、官方文档、Release 和作者明确关联的演示页寻找视频，记录来源页面、媒体地址或平台标识、作者、对应版本、检查日期以及可嵌入/仅外链/已失效状态。先验证视频确实展示这个项目及该项能力，再进入光盘；搜索命中和链接可访问都不等于演示已核对。

优先采用原作者允许嵌入的演示。没有可用录像时，选择能实际运行的试点自行复现录制，并说明环境、版本、操作和限制。暂时只有截图或图文说明的项目如实展示；**可信视频覆盖率是需要提高的内容质量指标，不能为了“全部有视频”用生成画面冒充运行。** 媒体下载和再分发依照原稿的授权边界执行。

## 15. 评论和收藏围绕正在做的项目

### 15.1 评论落在具体问题上

在普通讨论之外，允许评论关联资料的某一页、光盘的某一步、视频的某个时间点。求助可附版本、设备、实际输入、预期结果与失败截图，后来者能找到相同条件下的答案。

被采纳的修复经核对后回写对应步骤，保留贡献者、适用版本、日期及原讨论。资料换页或视频替换后，旧定位保留在旧版本并提示，避免把旧回答挂到错误位置。普通讨论、课程口碑原有对象和权限继续保留。

### 15.2 收藏成为我的项目清单

保留现有收藏夹与 STAR-02 成果，在其上试验“用于哪个项目”的关联。例如“社团报名工具”里有表单、身份验证、通知和导出四项需要，每项可以收藏候选方案、记录为什么选它，以及尚未尝试、已跑通、已接入或已放弃的状态。

同一份收藏可服务多个项目，用户仍能像现在一样普通收藏。优先补充选择理由、进度和下一步，使收藏能帮助完成作品；无需先做一套大型项目管理器。

## 16. 资料新闻与 AI 交付共同服务这条路径

### 16.1 资料从可找到到可拿来使用

补足课程、年份、版本、出处、上传者、审核者和时间；一套资料内的讲义、题目、答案、听力明确缺件情况。具备分享条件的文件提供站内预览与真实下载；只有外链的条目明确跳转目的，不用“下载”掩盖仅有链接。

原有规格和交接已记录本机资料袋、成套整理与 ZIP 下载等成果。**当前问题应逐个入口核对实际可达性、内容覆盖与用户使用结果，不能把已有成果误写成全部未实现，也不能用一次成功声称全库可用。**

内容选择优先贴近本校课程、竞赛与实际创作：经贡献者同意公开的操作记录、设备差异、课程经验及修正，比单纯增加仓库摘录更值得试验。缺失的资料允许用户提出需求，来源与审核沿用现有机制。

### 16.2 新闻说明变化以及下一步

精选内容至少说清楚：发生了什么、依据在哪里、谁会受影响、现在能做什么、有哪些限制。研究新闻也可以有价值，但需明确是否有代码、模型、样品或开放使用条件；论文结论、作者主张和编辑推断分开。

新闻可关联受影响的专辑或项目：上游升级、接口改变、依赖失效时，帮助维护者找出待重验步骤，用户按自己的订阅选择接收。没有值得发布的内容时允许不发，以可用信息和采取行动的价值评估摘要，不按每日凑够篇数评估。

### 16.3 AI 按具体交付结果验收

沿用已有原版角色、工作室、任务记录与恢复能力。北矿娘承担选材、理解与编辑，Codex 承担复现、验证与修复，是本轮建议分工；外部用户仍可把工作包交给自己的 AI。

先跑通一个范围明确的任务。例如“把这批允许使用的资料整理入库”，合格结果包含文件与来源、分类、可用预览、下载实测及发布状态回执；“做一张项目光盘”则包含中文步骤、版本、运行证据和演示。讨论完成、接口返回成功、任务进入终态，都不能单独代替这些结果。

失败指出具体卡点，保留已完成部分，能够续接；需要选择时给出项目简介、当前情况、建议与可选项，延续 Opus 第 23 次回信已做的请示改进。统计待处理、完成、失败与策略性跳过，并记录合格交付所需时间、人工修正和花费。完整自动化的范围随成功证据扩大。

## 17. 用一份光盘验证首个专辑假设

保持第 10 节的分期：P0 比较 3–5 个候选，P1 只完成一份高质量光盘。Codex 推荐的首个候选是：**把一批零散扫描资料整理成可查、可读、可下载的资料库。** 它直接服务本站已有需求，并可复用已有整理成果；最终是否采用请 Opus 与 Owner 共同判断。

试点交付限定为一份真实样例、一段可观看演示、最短复现路径、一个常见失败及恢复办法，以及能交给用户自己 AI 的工作包。以同一批可分享的样例展示处理前后；先核对既有导入、预览和下载，具体缺口再拟实施范围。收藏进度、定位评论可以先用内容模板验证需求，不必同时开发全部配套界面。

除第 11 节的同模型对照外，记录用户能否识别适用条件、完成首次任务、独立改动一个行为、再次下载打开结果，以及维护者修正一次内容所需的时间。站主自己跑通是内容生产检查，**不能替代另一位学习者的实际试用**。
