# 统一网站管理与 AI 执行：2026-10-09 验收

站主编辑、管理中心和两位角色的内容工具现在使用同一个发布服务。审核成功后公开页面读取的是新版本。此次暂停动画和人格改写，保留原 campus-companion 的记忆、人格、情绪、研究和工具程序。

## 使用入口

站主使用现有账号登录，从右下角“管理中心”进入 `/manage/`，或点击“编辑内容”搜索标题、项目与待审校圈。标有内容编号的原页面也有“编辑”按钮。新闻、项目、导读、校圈、公告、首页精选和页面 JSON 数据可编辑。完整字段保留分类与出处，配图支持上传、替换、预览、裁切焦点与完整显示。“版本记录与恢复”显示操作者、时间、内容与说明；恢复也产生新的版本和审计。

站主无需邮箱验证，自己的校圈帖子直接公开。普通同学保留原审核流程。两位不可登录的受保护系统身份通过私有桥接使用同一内容服务；相同昵称、邮箱后缀或普通 staff 标记不会自动授予这种权限。地点和公告原有检查条件保留，未核对的事项不能直接勾选跳过。

管理 UI 使用 [Django Unfold 0.108.0](https://pypi.org/project/django-unfold/0.108.0/)，复用 Django 5.2、本站 Member 与 Session。迁移 `0022_content_management` 增量添加覆盖层、历史和聊天任务，不替换数据库。

## 内容与来源

稳定编号：`entry/UUID` 是站内文章；`featured/编号` 是首页精选；`github/作者/仓库` 是已采集或静态目录项目；`page/名称` 是公开页面 JSON 数据。

外部项目和精选写入独立编辑覆盖层，重新采集仍更新上游统计。恢复第 0 版会清除覆盖，读取当前原始来源。站内文章通过既有保存、提交、审核与通知机制发布，保留原文件、来源和采集时间。机器人界面把旧“0%”明确称为“批次完整成功率”，实际新增、更新与上架数分别保留。

## 聊天执行

明确的审核、发布、修改和换图指令绑定发起窗口与持久化任务编号。普通聊天继续走原版程序。内容任务使用 `content_search`、`content_read`、`content_history`、`content_publish`、`content_review` 和 `content_task`，用目标编号与当前版本操作，避免旧自由参数工具反复报错。

两位角色使用原版 ToolAgent 和 writer，回复写入各自原版私聊历史。网站保存进度和回执，角色记忆仍在各自原数据库，不再建一套人格引擎。

- 完成状态必须引用本任务、同角色的成功发布或审核回执。明确列出多个目标时，回执必须覆盖全部目标。
- 非冲突字段修改最多重读并重试一次；冲突保留用户版本。超时先查状态，不能重复提交。
- 额度拒绝、调用错误和中断保留任务与原因，不自动提高额度。
- 执行与结论格式分别记录。已经成功的审核不会因模型漏用结构化结论而被误算失败；原告警保留。重启只核验回执，不重复写入。

实测修复了：管理表单来源被代理拒绝、首页标签切换丢失编辑参数、旧工具把 `entry/UUID` 当裸 UUID 后返回 HTML、结论格式告警误算执行失败、恢复旧覆盖没有移除后来新增字段。真实测试帖已撤回，审计与回复保留。

私有验收证据、备份、Cookie、数据库和模型配置在本机 `.data/`，不上传 GitHub。公开仓库包含源码、素材、测试、依赖和交接。没有新增公网部署。

新启动检查要求网站与 Hub 的 `managementVersion=1`、两位桥接 `bridgeVersion=28`；旧聊天版本号相同不再被当成已加载本次修复。依赖见 `campus/hub-requirements.txt`。

管理能力已经接通，模型仍可能误解复杂指令或需要目标澄清。采集全量覆盖、第三方工具安装和全站动画帧率不属于这次验收，不能从两次审核成功推断全站无人维护已达标。
