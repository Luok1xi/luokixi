# 调研：大学开发者需要什么样的资料站

> **当前统一入口：[PRODUCT_SPEC.md](PRODUCT_SPEC.md)。** Owner 最新要求先理清每个模块的效果，再开始制作。本文件保留历史调研与来源，旧优先级、规模数据、功能判断不作为当前实现或验收事实；第 21 次同步也不再是另一套总计划。

> **最新约定（2026-10-06，覆盖下文历史建议）：** 本站做学习引导，辅导走外部平台；复用 Django 账号与审核，支持可追溯匿名课评、教师/课程独立五星评分和高赞原话。全部布局由 Opus 负责，Codex 只负责功能侧代码。下文“无后端、仅 GitHub 实名、giscus 课评、不碰匿名”是早期方案，不再执行。当前接口见 REPUTATION_API.md，产品范围与验收统一见 PRODUCT_SPEC.md；旧规模数据和判断不是当前验收结果。

> 2026-10-06 · 方法：公开数据检索 + GitHub API 实测（Star 数为当天实时数据）+ 学术文献。
> 局限：这次没有做矿大（北京）学生的一手问卷。文末附了一份问卷草稿，建议上线前先发一轮。

## 一、结论先行

1. **需求真实存在，而且很大。** 985 高校学生自发建立的课程资料库，在 GitHub 上动辄几万 Star：浙大 4.1 万、清华 3.8 万、北大 3.4 万、中科大 1.6 万。北大校友写的《计算机自学指南》有 7.6 万 Star。
2. **矿大（北京）几乎是空白。** 和 cumtb 相关的仓库最高只有 27 个 Star，资料散落在十几个个人仓库里，大多是论文模板。矿大（徐州）稍好一些，有 `cumtcssuld/RSP_of_CUMTCS`（116 Star），还有新成立的 `OpenCUMT` 组织，可以作为合作对象。
3. **单纯的“资料仓库”容易断代。** 北大 libpku 最后一次推送在 2022 年，上交 SJTU-Courses 停在 2020 年。还在持续更新的项目（浙大、清华、HITSZ、南大智科）背后都有学生组织或明确的维护者，并且已经从“仓库”升级成了“网站”。
4. **学生最在意“有用”和“好上手”。** 一项对 803 名中国本科生的研究发现，持续使用开源社区的两个最强因素是感知有用（β = 0.369）和使用态度（β = 0.338），而易用性、低门槛试用、成果对同伴可见，又会反过来提升这两项。
5. **Luokixi 的差异化位置：资料 + 作品 + 刷题，三合一，面向一所学校。** 985 的同类项目大多只做其中一件事。我们已经有苹果级的视觉、GitHub 原生的投稿流程，并且不需要后端，冷启动成本很低。

## 三、985 高校的五种做法

**1. 资料仓库（浙大、清华、北大、中科大、上交）**
按课程分文件夹，存放试卷、笔记、实验报告。优点是门槛低、积累快。缺点是：
- 没有网站界面，不好搜索；
- 大文件撑爆仓库；
- 维护者毕业就停更（北大、上交的仓库都是这样）。

**2. 仓库汇总成网站（HITSZ OpenAuto、南大智科）**
每门课一个仓库，用 CI 自动把内容拉进 Hugo 或 VitePress 网站，再加上离线全文搜索（FlexSearch）和基于 GitHub Discussions 的评论（giscus）。这是最新的趋势，也最接近 Luokixi 的架构。

**3. 评课社区（中科大评课社区）**
从“选课讨论散落在 QQ 群里，没法沉淀”这个痛点出发。十年里积累了 3.7 万条评价，2025 年还扩展成了跨校平台。说明“课程评价”是独立的强需求。

**4. 手册与自学路线（上交生存手册、计算机自学指南）**
不收资料，而是写“怎么过好大学 / 怎么学”。自学指南的 Star 数是所有同类项目里最高的，说明“路线图”比“资料堆”传播力更强。

**5. 技术社团做基础设施（清华 TUNA 镜像站、中科大 LUG、复旦旦夕 App）**
学生社团长期运营一个大家每天都在用的工具，社团本身就是维护者，不会断代。

## 五、给 Luokixi 的定位建议

**一句话：矿大（北京）学生的“资料、作品、刷题”主页。**

- **比资料仓库多走一步**：不是把文件堆进仓库，而是一个能搜索、能评价、能展示作品的网站。
- **比评课社区多一种身份**：评价、项目、刷题记录都挂在同一个 GitHub 账号下，能直接写进简历。
- **不碰匿名社区**：树洞类匿名平台的审核与合规风险高。我们坚持实名（GitHub 账号）、可追溯、PR 审核。

## 七、风险

1. **版权**：试卷和真题的公开方式需要谨慎。建议校内资料只收录“学生自己整理的”或“老师同意公开的”，其余只做目录。
2. **断代**：毕业季是最大的风险。对策是每门课设“课代表”，并且在 README 里写清交接流程。
3. **访问速度**：GitHub 在部分校园网环境下访问不稳定。上线后应该实测；如果慢，再评估国内的部署方式（静态站点可以整体迁移）。
4. **数据抓取**：洛谷、力扣都没有正式的公开 API，页面结构随时可能变化。构建脚本已经做了“失败时沿用旧数据”，不会让整站挂掉，但需要有人定期检查。

## 八、问卷草稿（建议发给矿大北京的同学）

1. 你是哪个学院、哪一级？
2. 你现在从哪里获取历年试卷和复习资料？（QQ 群 / 网盘 / 学长学姐 / 其他）
3. 找资料时最头疼的是什么？（找不到 / 不全 / 过时 / 不知道哪个靠谱）
4. 选课时，你最想知道一门课的什么信息？（给分 / 作业量 / 老师风格 / 考试形式）
5. 你参加过哪些竞赛？组队时遇到过什么困难？
6. 你在洛谷、力扣、Codeforces 上刷题吗？希望和同学一起排名吗？
7. 你有没有想展示的项目（课设、竞赛作品、实验室项目）？
8. 你有 GitHub 账号吗？提交过 Pull Request 吗？
9. 如果有一个矿大（北京）的资料站，你最希望第一天就看到什么？
10. 你愿意做某门课的“课代表”（资料维护者）吗？
